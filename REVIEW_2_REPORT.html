1. System Architecture

CreatorOps is architected as a three-tier web application structured around the Model-View-Template (MVT) pattern and RESTful application programming interfaces.

Figure 1: High-Level Three-Tier Architecture of CreatorOps

1.1 Presentation Tier

The client interface is rendered through responsive server-side HTML5 templates utilizing CSS variables for styling. It provides operational screens for workspace configuration, client brand records, marketing campaigns, content drafting, and approval queues. External clients and automated tools interact via JSON-based REST endpoints over HTTPS.

1.2 Application Tier

The application tier is powered by Python 3.12 and Django 6.1. It manages routing, tenant isolation, session validation, and content state transitions. A Django REST Framework (DRF) layer exposes ModelViewSets for programmatic operations. In addition, an internal rule-based agent module (agents/) provides automated checks on creator scripts—measuring word count, estimated speaking duration, hook keyword presence, and brand safety compliance. Direct Social Publishing engine interfaces with Meta Graph, YouTube, and TikTok APIs. WhiteNoise serves static assets directly from the WSGI application layer.

1.3 Persistence Tier

Persistent relational data is stored in PostgreSQL for production deployment, with SQLite supported for local development. Binary assets (images, documents, and videos) are managed with support for Amazon S3 object storage via boto3 and django-storages.

2. Cloud Architecture

The production application is hosted on Vercel's cloud infrastructure, taking advantage of its edge routing network and serverless execution capabilities.

Figure 2: Cloud Deployment Model on Vercel Serverless Edge Platform

2.1 Ingestion and Execution Pipeline

  • DNS and Edge Ingestion: Traffic is routed through Vercel's Anycast edge network with automatic TLS/SSL termination.
  • Serverless Execution: Incoming requests execute within Python 3.12 serverless functions via the standard WSGI interface (config/wsgi.py).
  • Static Asset Offloading: Bundled CSS, JavaScript, and diagrams are cached and served from Vercel's content delivery network points of presence.
  • Database Connectivity: The serverless runtime connects to a managed PostgreSQL database via connection pooling using the DATABASE_URL environment variable.

4.1 Cardinality Overview:

  • Workspace to Membership: One-to-Many ($1 : N$). A workspace maintains multiple user memberships.
  • Workspace to Client: One-to-Many ($1 : N$). A workspace holds multiple client brand profiles.
  • Client to Campaign: One-to-Many ($1 : N$). A client sponsors multiple marketing campaigns.
  • Campaign to ContentItem: One-to-Many ($1 : N$). A campaign contains multiple content deliverables.
  • ContentItem to ContentVersion: One-to-Many ($1 : N$). Each edit generates a sequential revision record.
  • ContentItem to Approval: One-to-Many ($1 : N$). An item records internal manager and client review decisions.
  • ContentItem to SocialPublishLog: One-to-Many ($1 : N$). An item tracks direct social publications across Meta Graph, YouTube, and TikTok.

5. Module Design

The software follows a domain-driven structure, separated into distinct Django apps:

  • accounts: Authentication, session management, user registration, and profile data.
  • workspaces: Multi-tenant organizational boundaries, member roles, and tenant context resolution.
  • clients: Client brand profiles, contact details, and brand voice guidelines.
  • campaigns: Marketing campaign objectives, budget allocations, and status tracking.
  • content: Deliverable management, social platform targeting, and revision snapshotting.
  • approvals: Two-tier review workflow (Manager Gate followed by Client Sign-off).
  • assets: Media asset handling and cloud storage integration.
  • analytics: Dashboard KPI aggregation and performance reporting.
  • agents: Automated script auditing, hook suggestions, and comment clustering.
  • config: Root URL routing, project settings, and WSGI entrypoint.

7. Authentication

The system implements a four-tier Role-Based Access Control (RBAC) model integrated with multi-tenant data boundaries:

  • Password Protection: Passwords are stored as salted PBKDF2-SHA256 hashes (390,000 iterations).
  • Session Isolation: Sessions are validated with CSRF protection on all state-modifying requests.
  • Tenant Boundaries: The active workspace is resolved per request. Database operations automatically filter by workspace ID to ensure tenant data isolation.
  • Role Definitions:
    1. Admin: Global control over workspace settings, members, and roles.
    2. Manager: Client brand setup, campaign creation, primary draft approvals, and direct social publishing.
    3. Creator: Content drafting, script versioning, automated script checking, and asset uploads.
    4. Client Reviewer: Read-only access to campaign deliverables with final approval sign-off.

8. Core Modules

  • Content Lifecycle State Machine: Programmatically manages content transitions across 8 stages: draft → pending_manager → changes_requested → pending_client → approved → scheduled → published.
  • Revision Snapshots: Every script or caption change generates an immutable ContentVersion record, maintaining a complete audit trail.
  • Automated Script Analysis: The script review module checks text against word count limits, spoken duration pacing (~130 wpm), hook keyword placement in the opening sentence, and forbidden brand terms.
  • Direct Social Publishing: Native integration with Meta Graph API v19.0 (Instagram Reels / Feed), YouTube Data API v3 (Shorts), and TikTok Content Posting API v2 with automatic post ID and permalink generation.
  • Competitor Intelligence & Benchmarking: Gathers public video telemetry from rival channels and computes a Head-to-Head Performance Matrix.
